# NStack napplet runtime v1

Canonical additive backend wire contract. Online only. Client networking belongs to SyncService; views consume local stores/live queries. NIP-98 and FIPS transport remain unchanged. Namespaces never grant access.

Base `B=/api/v4/flightdeck-pg/workspaces/:workspaceId/apps/:appNpub/napplets`. The application must match the workspace registered application; napplet IDs are durable `[a-z][a-z0-9_-]{0,63}` slugs independent of names/versions. Authenticated agents remain themselves.

- `GET B?limit=50&after=<napplet slug>` → `{installations,next_cursor}`; only audience/publisher/manager-visible installations, limit 1–200.
- `PUT B/:nappletId` creates installation with `{expected_revision:0,requester_npub,publisher_npub,display_name,bundle:{file_id,file_version_id,sha256_hex},manifest:<frozen manifest v3>,delegation_id?}`. Manager authority required; requester-only audience, one installation per workspace/application/napplet. Publishers cannot forge identity. Creation never grants personal capabilities or collection access.
- `GET B/:nappletId` → `{installation}`. All mutations return this envelope unless specified.
- `PATCH B/:nappletId` `{expected_revision,display_name?,audience_npubs?}` installation owner or delegated manager only, current workspace members only. Audience is discovery/open only.
- `POST B/:nappletId/releases` `{expected_revision,bundle,manifest}` authenticated registered publisher only. Integrity is checked against the completed immutable NStack File version. Old releases retained. Expanded manifest capabilities or collection schema/access declarations stage a pending release; no implicit personal grant. Same approved declarations activate automatically regardless of digest changes.
- `POST B/:nappletId/releases/approve` `{expected_revision}` manager approves pending declarations; this does not approve personal capabilities.
- `DELETE B/:nappletId` JSON `{expected_revision,data:"keep"|"delete",confirm_napplet_id?}` installation owner or delegated manager only. Delete requires exact confirmation and ownership of all collections; deletes collection payload/history only, never source Files/history. Keep retains collections and reconnects on reinstall.
- `POST B/:nappletId/collections` `{name,scope:"personal"|"team",schema_version,read_npubs:[],write_npubs:[]}` → `{collection}`. Owner is authenticated actor, never client supplied. Explicit team sharing; private default. Unique name per owner/scope/napplet. Audience does not grant data access.
- `GET B/:nappletId/collections?limit=50&after=<UUID>` → `{collections,next_cursor}` authorized collections only.
- `PATCH B/:nappletId/collections/:collectionId` `{expected_revision,read_npubs?,write_npubs?}` owner only; complete replacement supports revocation. Every delegate must remain a workspace member. No implicit workspace-owner read.
- `GET B/:nappletId/collections/:collectionId/records?limit=50&after=<record id>` → `{records,next_cursor}`. Stable record-ID keyset pagination, no offset or implicit unbounded query.
- `PUT B/:nappletId/collections/:collectionId/records/:recordId` `{expected_revision:0|N,schema_version,data}` → `{record}`. Zero creates; exact revision updates, conflicts 409. IDs 1–128 safe characters. No client metadata/owner/namespace overrides. History retained transactionally.
- `DELETE` same record path `{expected_revision}` → `{record}` tombstone. Deleted IDs cannot be recreated with revision zero.
- `GET` same record path → `{record}`; `/history?limit=50&after=<revision>` → `{versions,next_cursor}` with current collection read permission.
- `POST B/:nappletId/collections/:collectionId/migrations` `{expected_revision,from_schema_version,to_schema_version,compatible:true,source:{file_id,file_version_id,sha256_hex},records:[{id,data}]}` owner only. Explicit bounded (200) import from a readable immutable File version; source originals/history are untouched. Atomic, create-only record import; records conflict rather than overwrite. Imported records retain provenance. Incompatible/destructive migrations are rejected pending an explicit future protocol.

Responses carry server-controlled workspace/application/napplet/collection/owner/revision metadata. Errors `{code,error}` with 400 invalid inputs, 403 denied, 404 unavailable, 409 revision/identity/schema conflicts. JSON object records bounded to 256 KiB. Every operation rechecks membership, installation state and audience; collection grants additionally gate data. Managers cannot read personal collections by role.

Personal host signer capabilities are outside these backend data grants. No signer, raw key, relay fetch, decrypt, DM send, plaintext persistence or agent-DM authority is provided by these routes. Hosts must implement and separately approve supported personal capabilities; unsupported requests must remain explicit failures.

Implementation: `src/routes/napplets.ts`, `src/services/napplets.ts`, `src/schema/napplets.sql`, public types in `src/types.ts`, OpenAPI in `src/openapi.ts`. Existing org-data, compatibility app rows and File storage remain unchanged.

Manifest is exactly Ambulando `docs/design/napplet-runtime-v3.md` / manifest.json fixture: version:3, stable napplet_id slug, bundle_version,title,icon,runtime:{protocol:3,min_host},collections object {name:{scope,schema_version,operations}},capabilities object {name:{version,resources,operations}}. Backend enforces declared operations in addition to collection grants. Frame base_revision maps explicitly to HTTP expected_revision. Installation revisions and record revisions are independent. Expansion approval requires a human manager.

`GET B/:nappletId/bundle` is the authenticated audience-bound byte endpoint. It serves only the active immutable File version, rehashes bytes, checks exact v3 manifest equality against approved server declarations, and returns application/octet-stream with nosniff/attachment/no-store. Host verifies bytes and renders in its isolated frame. Audience grants this exact published bundle read, never arbitrary File/data access. `GET B/:nappletId/releases?limit=50&after=<revision>` returns `{releases,next_cursor}` for accessible installations; previous immutable version metadata is retained for deliberate publisher rollback via normal release validation. Installation owners may manage their own audience/removal; fresh install still requires actual workspace app-management authority.

ACL mapping: fresh/reinstall and manager approval require the existing canonical `napplet.install` workspace permission, or a current owner-issued scoped `wapp.manage` delegation. A workspace owner role alone does not replace a revoked install grant. Publication requires both the installation-selected authenticated publisher and its current canonical `napplet.publish` permission plus read access to the source File channel. Initial installation validates that publisher authority and requester membership. Existing org-data `org_data.read/write/schema` never grants personal collection access; no new default rights are seeded. Installation owners may share/remove their own installation; this still grants no collection access, and delete-data requires ownership of every target collection.

Cross-device reconnect: `GET B/:nappletId` returns removed lifecycle metadata (`removed:true`, current `revision`) only to the original owner/publisher or current authorized installation manager. Removed entries stay out of ordinary lists; their bundle/data routes remain unavailable. Reinstall uses that exact revision in PUT, preserving stable owner/publisher and retained collections. Former audience alone cannot discover removed metadata.
